# Database specification

Planning baseline: November 4, 2026. This document defines PostgreSQL persistence for v1. It contains specifications and migration examples, not an implemented schema. [ARCHITECTURE.md](ARCHITECTURE.md) owns service boundaries; [SQUARE_INTEGRATION.md](SQUARE_INTEGRATION.md) owns source interpretation; [API_CONTRACTS.md](API_CONTRACTS.md) owns transport names.

## Conventions and invariants

Use PostgreSQL 17, Prisma, UUID internal primary keys with `DEFAULT gen_random_uuid()`, `timestamptz(6)` instants, and explicit IANA timezones. Never store a local timestamp as if it were UTC. All rows below have `id uuid PK` and `created_at timestamptz NOT NULL DEFAULT now()` unless a different primary key is stated. Mutable master/header rows also have `updated_at timestamptz` and `version integer NOT NULL DEFAULT 1`; update with optimistic concurrency and increment `version`. Immutable event/ledger/snapshot rows have no editable version.

`R` below means `restaurant_id uuid NOT NULL`; `L` means `location_id uuid NOT NULL`. Every location-scoped business row has both. Each tenant-owned parent exposes `UNIQUE(restaurant_id,id)`; each location-owned parent exposes `UNIQUE(restaurant_id,location_id,id)`. Children use matching composite foreign keys, so supplying a valid ID from another restaurant or location fails in PostgreSQL as well as in services. `locations` exposes `UNIQUE(restaurant_id,id)`. A connection-scoped child also carries `connection_id` with a matching tenant FK. UUID identity by itself is never authorization.

In field lists, `?` means nullable and all other fields are NOT NULL unless an explicit alternative is stated. Bare name/label/status/source/hash/ref/code/note fields are `text`; enums are PostgreSQL enums or checked text with exactly the listed values. Internal `_id` references are UUID; fields explicitly named `square_*_id` and source IDs are opaque text. `_at` fields are `timestamptz`, `_date` fields are `date`, flags are boolean, counters/minutes/positions are integers, quantity fields use the Decimal quantity type above, and `_cents` fields use bigint. Defaults apply only where listed or in this convention; optional values do not silently become zero. Prisma uses explicit `@map`/`@@map` for these snake_case names.

Use `ON DELETE RESTRICT` for business history and referenced master data; archive through `archived_at` or explicit statuses. Only disposable Auth.js session/token records and never-posted draft child rows may cascade when their dedicated service deletes the parent. Users with history are disabled, not deleted. Membership authorization is checked on each server operation. Do not add row-level-security policies that are never configured correctly: application scoping plus composite FKs is the v1 isolation mechanism, with mandatory cross-tenant tests.

| Value | PostgreSQL / Prisma representation | Rules |
| --- | --- | --- |
| Money amount | `bigint` / `BigInt` | Integer minor units; USD only in v1, currency `char(3)` checked `USD`. API serializes as decimal strings. Never JS `number` for accounting. |
| Ingredient or order quantity | `numeric(20,6)` / `Decimal` | Signed for ledger; positive for recipe/receipt quantities. Reject more than six fractional digits at input. |
| Cost per base unit | `numeric(24,12)` / `Decimal` | Nullable means unknown; explicit zero is a known zero cost. Round only final display/report minor units. |
| Percent/factor | `numeric(12,8)` / `Decimal` | Loss fraction in `[0,1)`; multiplicative factors positive. |
| Square version | `bigint` / `BigInt` | Never convert to floating point. Source IDs are opaque `text`. |
| Date / local time | `date`, `time(0)` | Business date and configured opening/cutoff wall time only, not instants. |
| Payload | `jsonb` | Explicit sanitized allowlist; bounded size; never credential, PAN, payment token, customer profile, or unrestricted raw SDK object. |

Every FK used for list queries gets a supporting B-tree index. Standard location lists use `(restaurant_id,location_id,created_at,id)`; time reports use `(restaurant_id,location_id,effective_at,id)`. Do not create a second index whose leading columns are already served by a unique index unless an explain plan justifies it. Keep source ID uniqueness independent of mutable location assignment.

## Square import and synchronization tables

Square IDs are unique within a merchant/environment connection. Catalog objects are merchant-scoped and can apply to multiple locations; do not impose a location on catalog identity. `square_connection_locations` binds imported locations explicitly even though v1 enables one. Historical IDs survive reconnect/token rotation; rotating credentials updates secret references, not connection identity.

Ingredient identity is restaurant-wide; stock, reorder policy, purchasing, recipes, and costs are location-scoped. V1 forms select the single active location, but persist it. No nested recipes/subrecipes in v1: recipe components reference raw ingredients only, eliminating cycles and ambiguous yield expansion.

Canonical expansion: `required_base_qty = component.quantity_base / recipe_version.yield_servings / (1 - loss_fraction) * sold_quantity`; add/subtract mapped modifier deltas using documented Square modifier quantity normalization. A modifier recipe's yield is fixed to 1. No mass-volume conversion without an explicit ingredient-specific package conversion; v1 does not infer density. `each` may be fractional when the restaurant models divisible portions, consistently to six digits.

Perform expansion and ingredient coalescing in a dedicated Decimal math helper configured to 50 significant digits and HALF_UP rounding, then quantize the desired total once per sale-line/ingredient to six places. Compute ledger delta as `new_quantized_desired - previous_quantized_desired`; never round independent deltas or each intermediate component. Cost uses the same quantized usage multiplied by the recorded 12-place minor-unit rate, summing at working precision then rounding once per sale line to integer cents. Any derived quantity, rate or money amount outside its storage/API bounds, including a receipt's derived rate beyond numeric(24,12), is rejected as validation 422 before insertion; never let database overflow become an unexplained 500.

Quantity completeness is a whole-line decision. If the base recipe is missing, any selected modifier has an unknown ingredient effect, or the expanded configured requirement is negative, set `QUANTITY_UNKNOWN` with reasons and do not post a guessed partial deduction. For a newly seen unknown line, create no consumption movements. For an already applied line that becomes unknown, preserve the last known `sale_consumption_states` and mark the current source projection stale/incomplete; do not reverse those states to zero. Resolving the mapping recomputes the whole line and appends only the difference from that preserved state. Missing ingredient cost alone still permits known-quantity posting and sets cost UNKNOWN/PARTIAL. Explicit source cancellation or line removal reverses the last applied quantities even when the recipe/mapping is now unavailable. Snapshot/source per-line quality distinguishes these cases from a true known zero requirement.

Receipt posting locks the PO header/lines, validates outstanding quantities, inserts stock and cost-history rows, changes receipt/PO states, and writes the audit row in one transaction. V1 rejects overdelivery; staff must amend the ordered quantity with reason before posting. A posted receipt is immutable. Reversal appends exact opposite movements, preserves the original, restores PO outstanding quantity, and makes its cost entry ineligible prospectively without mutating historic cost snapshots. Corrections are replacement receipts plus explicit reasons. An opening stock count establishes physical stock; an opening cost establishes cost independently.

Purchasing reporting is event-date based: original posted receipt cost remains positive gross spend on its original server posted date, even after a later reversal. A linked reversal receipt contributes negative net spend on its own server posted date. Expose `grossReceivedCents`, nonnegative `reversedCents`, and `netReceivedCents = grossReceivedCents - reversedCents` for each requested period; do not retrospectively drop an original receipt merely because its current status is REVERSED. Current PO accepted received quantity remains original quantities minus linked reversal quantities regardless of reporting period. Reversal records retain exact original line costs/fees so this treatment is reproducible.

Reservation allocation SQL is a database safety net. Also require header `CHECK(starts_at < expected_ends_at)` and nonnegative buffer snapshot checks. Use a custom migration because Prisma schema syntax must not be assumed to express all PostgreSQL features. [Prisma migration guidance](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/unsupported-database-features) describes retaining custom SQL in committed migrations. [PostgreSQL range constraints](https://www.postgresql.org/docs/17/rangetypes.html#RANGETYPES-CONSTRAINT) support overlap prevention.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE reservation_allocations
  ADD CONSTRAINT allocation_positive_interval
    CHECK (occupied_starts_at < occupied_ends_at),
  ADD CONSTRAINT seated_presence_requires_active
    CHECK (NOT seated_active OR active),
  ADD CONSTRAINT no_overlapping_active_table_allocations
    EXCLUDE USING gist (
      restaurant_id WITH =,
      location_id WITH =,
      table_id WITH =,
      tstzrange(occupied_starts_at, occupied_ends_at, '[)') WITH &&
    ) WHERE (active);

CREATE UNIQUE INDEX one_seated_party_per_physical_table
  ON reservation_allocations(restaurant_id,location_id,table_id)
  WHERE seated_active;
```

For a confirmed booking, `occupied_starts_at = starts_at - pre_buffer`; after seating, `occupied_starts_at = min(starts_at,seated_at) - pre_buffer`. `occupied_ends_at = expected_ends_at + post_buffer`. On SEAT, preserve scheduled starts_at, assign seated_at=server now, and set expected_ends_at to `max(existing expected_ends_at,seated_at + selected duration)`. Default selected duration is the reservation's stored meal duration; persist `duration_minutes_snapshot` on reservations for this purpose. Atomically extend all claims under the same allocator lock/exclusion constraint; conflict rolls back seating entirely. This prevents early seating leaving an unclaimed physical interval and late seating losing the promised meal duration. A seated extension through PATCH must similarly reallocate or return 409.

End-exclusive ranges permit touching boundaries. The constraint blocks concurrency across public bookings, staff edits, walk-ins, waitlist seating, and multi-table combinations. Map PostgreSQL `23P01` to `SLOT_UNAVAILABLE`, never to a generic 500. Lock a location booking-settings row before allocation or configuration changes, select least excess capacity, then fewest tables, then lexical table label/ID, validate capacity/hours/blocks inside the transaction, insert all rows, and commit atomically. UI availability is a suggestion, never a lock. There are no public holds in v1.

Use a location-scoped lock for reservation/table/settings changes and bounded retries for serialization/deadlock failures. A seated party extending into another reservation cannot displace it: return conflict and require staff to choose another available allocation or contact the affected guest. No emergency bypass removes the exclusion constraint.

Finite expected intervals are planning estimates, not automatic physical releases. SEAT checks that every selected physical table has no other seated_active claim, then sets seated_active=true on all its rows atomically; COMPLETE (“Table cleared and ready”) clears seated_active and active. The named partial unique index also rejects a direct/concurrent second seating with nonoverlapping planned times; map that named 23505 violation to TABLE_OCCUPIED, not an unrelated generic unique error. PATCH of a seated allocation moves presence claims atomically along with its time claims. An overdue SEATED reservation whose expected end is before server now conservatively makes its physical tables unavailable for all new allocations, including future dates, until a host extends/reassigns/clears it. Existing future confirmed bookings remain records, but seating them cannot bypass actual seated presence. Public/staff availability and booking use the same conservative rule; a clock tick never silently clears a seated party.

## Temporal integrity and projection boundaries

Published recipe and mapping ranges use exclusion constraints analogous to table allocations, on their identity columns and `tstzrange(effective_from,effective_to,'[)')`; null upper bound means unbounded. A draft version is excluded from enforcement until publication. Publishing closes the previous range and opens the new one in one transaction under recipe/mapping locks. Use a partial unique index for one draft version per recipe, and composite FK protections for every recipe component and mapping.

Required temporal SQL shapes (alongside tenant composite FKs and ordinary Prisma columns):

```sql
ALTER TABLE recipe_versions
  ADD CONSTRAINT recipe_published_has_interval CHECK (
    status = 'DRAFT' OR
    (effective_from IS NOT NULL AND
     (effective_to IS NULL OR effective_to > effective_from))
  ),
  ADD CONSTRAINT recipe_effective_intervals_do_not_overlap
    EXCLUDE USING gist (
      restaurant_id WITH =, location_id WITH =, recipe_id WITH =,
      tstzrange(effective_from,effective_to,'[)') WITH &&
    ) WHERE (status IN ('PUBLISHED','RETIRED'));

CREATE UNIQUE INDEX one_recipe_draft
  ON recipe_versions(restaurant_id,location_id,recipe_id)
  WHERE status = 'DRAFT';

ALTER TABLE recipe_mappings
  ADD CONSTRAINT mapping_positive_interval CHECK
    (effective_to IS NULL OR effective_to > effective_from),
  ADD CONSTRAINT mapping_effective_intervals_do_not_overlap
    EXCLUDE USING gist (
      restaurant_id WITH =, location_id WITH =, connection_id WITH =,
      catalog_square_id WITH =, kind WITH =,
      tstzrange(effective_from,effective_to,'[)') WITH &&
    );
```

`business_day_policies` has the same positive-interval/exclusion shape on `(restaurant_id,location_id)` without a status predicate. `recipe_mappings` additionally checks `(kind='VARIATION' AND recipe_id IS NOT NULL AND NOT no_ingredient_effect) OR (kind='MODIFIER' AND ((recipe_id IS NOT NULL AND NOT no_ingredient_effect) OR (recipe_id IS NULL AND no_ingredient_effect)))`; the NO_EFFECT branch requires nonnull acknowledgement actor/reason. Retired recipe versions retain effective intervals and continue to guard history. To avoid a future-dated publish accidentally retiring today's active version, status is lifecycle metadata; active version selection always evaluates its effective interval.

Reported business dates are stored with the applicable timezone/cutoff policy snapshot when a sale is projected. Reconciliation does not recompute old dates using today's settings. Square source created/update timestamps, source close timestamp, financial refund timestamp, imported timestamp and stock effective timestamp are distinct columns. Missing original device time is reported as a limitation, never guessed.

All financial and quantity projections use a revision/input hash. A transaction locks the current order projection, compares desired normalized state with applied state, appends only delta stock movements, writes cost snapshot revisions, updates applied state, and records audit/job completion. Reprocessing identical state performs no business mutation. Refund reporting and receipt reversal source identity are independently unique. A transaction rollback leaves no partial stock/receipt/reservation or audit commit.

## Retention, backup, and repair

Reservation/waitlist contact and notes are anonymized 90 days after a fixed retention anchor, unless an explicitly documented operational retention exception is set. Reservations set terminal_at on CANCELED/NO_SHOW/COMPLETED; waitlist entries set it on LEFT/CANCELED/SEATED. Terminal timestamps do not change when notes or unrelated metadata are edited. Without a terminal timestamp, a past reservation uses expected_ends_at; an abandoned waitlist entry uses joined_at. Redact when anchor+90 days is reached; protect active bookings whose expected end is still in the future. This allows stale never-completed past records to age out without retaining contacts indefinitely. Supplier contacts and user identities are retained while active. Audit logs omit guest contact from creation onward; retention jobs log record counts, never erased values. Signed normalized webhook envelope/payload detail retains 30 days; keep event identity/hash and processing result for durable deduplication. Successful job payloads may be redacted after 30 days while source/posting uniqueness remains. Retain financial/stock history for seven years as a product operational default, subject to owner-approved policy before launch; this is not tax/legal advice.

Managed PostgreSQL must offer encrypted backups plus point-in-time recovery. Target RPO 15 minutes and RTO four hours, verified by a staging restore drill. Before restore: stop job claims/public writes, preserve post-backup exports if available, snapshot current DB, record cutoff and incident ID. Restore to an isolated database, apply compatible migrations, verify constraints/row counts/ledger/report fixtures, rotate application connection, then replay Square safely from a conservative watermark. Restore reservations and locally entered receipts from backup/manual front-desk records; Square cannot reconstruct them. Keep public booking disabled until reservations are reconciled, to avoid accepting conflicting bookings during recovery.

Deployment-controlled `MAINTENANCE_MODE` disables business writes/public booking and worker effect execution during recovery; it is not user-supplied API data. Record each rehearsal as a `RECOVERY_DRILL` audit action with sanitized target database alias/ID, drill timestamp, measured RPO/RTO, outcome and evidence reference. No credentials/connection URI appear in that metadata. Authenticated health reads the latest relevant drill action plus fresh operational_state heartbeats; public health exposes no internals.

Repairs run through audited service commands with dry-run counts and bounded tenant/location/time range. Never manually delete duplicate sale movements or rewrite source totals to force reconciliation. Compare desired projection to applied state and append corrective revisions; preserve the issue, reason, operator and run ID. Inventory repairs after a physical count obey the anchor rule. After credential compromise, rotate secret references and signing keys, invalidate sessions as necessary, audit access, and replay unprocessed inbox records without accepting unsigned events.

## Database acceptance checklist

- Fresh database migrates and seeds; production-like backup restores with all custom constraints intact.
- Cross-restaurant and cross-location children fail at composite FKs; every repository query scopes by R/L.
- Two postings of the same receipt/source revision yield one effect; changed payload under an idempotency key fails.
- Two overlapping table allocations cannot commit, including overlapping combinations and direct SQL insertion.
- Numeric precision, unknown/zero costs, temporal mapping overlap, reversal uniqueness and archival rules are verified in PostgreSQL tests.
- No source secret, customer card data, credential token or raw unrestricted Square payload appears in tables or logs.
